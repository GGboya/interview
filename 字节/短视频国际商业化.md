### 1. Redis RDB持久化机制

**问题：** RDB在保存快照的时候，这时候有新的写入，Redis是怎么做的呢？

**答案：**

**核心机制：Copy-on-Write（写时复制）**

**详细流程：**
1. **fork子进程：** Redis主进程fork一个子进程来执行RDB操作
2. **内存共享：** 子进程和父进程共享相同的内存页面
3. **写时复制：** 当主进程有写操作时，操作系统会为修改的内存页创建副本
4. **异步保存：** 子进程基于fork时的内存快照进行RDB文件生成

**具体实现：**
```c
// Redis RDB保存流程
int rdbSave(char *filename) {
    pid_t childpid;
    
    if ((childpid = fork()) == 0) {
        // 子进程：保存RDB
        rdbSaveBackground(filename);
        exit(0);
    } else {
        // 父进程：继续处理客户端请求
        server.rdb_child_pid = childpid;
        return C_OK;
    }
}
```

**优点：**
- 主进程不会被阻塞，可以继续处理客户端请求
- 保证数据一致性：RDB文件反映fork时刻的数据状态
- 高效：只有写操作才触发内存页复制

**注意事项：**
- 如果写操作频繁，COW会增加内存使用
- fork操作本身有微小的延迟

#### sync.RWMutex（读写锁）底层实现
**核心数据结构：**
```go
type RWMutex struct {
    w           Mutex  // 写锁
    writerSem   uint32 // 写者等待信号量
    readerSem   uint32 // 读者等待信号量
    readerCount int32  // 读者计数器
    readerWait  int32  // 写者等待的读者数量
}
```

**底层实现原理：**

1. **读锁获取（RLock）：**
   ```go
   func (rw *RWMutex) RLock() {
       if atomic.AddInt32(&rw.readerCount, 1) < 0 {
           // 有写锁等待，当前读者需要等待
           runtime_SemacquireMutex(&rw.readerSem, false, 0)
       }
   }
   ```

2. **读锁释放（RUnlock）：**
   ```go
   func (rw *RWMutex) RUnlock() {
       if r := atomic.AddInt32(&rw.readerCount, -1); r < 0 {
           // 可能是最后一个读者，需要唤醒等待的写者
           rw.rUnlockSlow(r)
       }
   }
   ```

3. **写锁获取（Lock）：**
   ```go
   func (rw *RWMutex) Lock() {
       rw.w.Lock() // 先获取写锁，防止多个写者
       // 将readerCount设为负数，阻止新的读者
       r := atomic.AddInt32(&rw.readerCount, -rwmutexMaxReaders) + rwmutexMaxReaders
       if r != 0 && atomic.AddInt32(&rw.readerWait, r) != 0 {
           // 等待现有读者完成
           runtime_SemacquireMutex(&rw.writerSem, false, 0)
       }
   }
   ```

**关键技术点：**
- **readerCount**：正数表示读者数量，负数表示有写者等待
- **原子操作**：使用atomic包保证计数器操作的原子性
- **信号量**：使用runtime信号量实现goroutine的阻塞和唤醒
- **写者优先**：通过将readerCount设为负数来阻止新读者

#### sync.Map（并发安全的map）底层实现

**核心设计思想：读写分离 + 延迟同步**

**数据结构：**
```go
type Map struct {
    mu     Mutex                    // 保护dirty的互斥锁
    read   atomic.Value             // 存储readOnly，原子读取
    dirty  map[interface{}]*entry   // 完整数据集，需要加锁访问
    misses int                      // read未命中计数器
}

type readOnly struct {
    m       map[interface{}]*entry  // 只读map
    amended bool                    // dirty是否包含read没有的新key
}

type entry struct {
    p unsafe.Pointer  // 实际指向数据的指针
}
```

**数据流转过程详解：**

**初始状态：**
```
read:  {} (空)
dirty: {} (空)  
misses: 0
```

**场景1：第一次写入数据**
```go
m.Store("user", "alice")
m.Store("role", "admin")
```

**数据流转：**
```
操作：Store("user", "alice")
1. read中没有"user" 
2. 加锁，在dirty中创建entry
3. 设置amended=true (dirty有read没有的数据)

read:  {amended: false}
dirty: {"user": &entry{p: "alice"}}
misses: 0

操作：Store("role", "admin")  
read:  {amended: false}
dirty: {"user": &entry{p: "alice"}, "role": &entry{p: "admin"}}
misses: 0
```

**场景2：读取操作触发miss计数**
```go
value := m.Load("user")  // goroutine 1
value := m.Load("role")  // goroutine 2  
value := m.Load("dept")  // goroutine 3
```

**数据流转：**
```
Load("user"): read中没有 → 加锁查dirty → miss++
Load("role"): read中没有 → 加锁查dirty → miss++  
Load("dept"): read中没有 → 加锁查dirty → miss++，但dirty中也没有

read:  {amended: false}
dirty: {"user": &entry{p: "alice"}, "role": &entry{p: "admin"}}
misses: 3  // 达到阈值len(dirty)
```

**场景3：dirty提升为read（关键优化）**
```
当 misses >= len(dirty) 时，触发提升：
1. 将dirty内容复制到read
2. 清空dirty
3. 重置misses为0
4. 设置amended=false

提升后：
read:  {
    m: {"user": &entry{p: "alice"}, "role": &entry{p: "admin"}},
    amended: false
}
dirty: nil
misses: 0
```

**场景4：高性能无锁读取**
```go
// 现在所有读操作都是无锁的！
value := m.Load("user")  // 直接从read读取，无需加锁
value := m.Load("role")  // 直接从read读取，无需加锁
```

**数据流转：**
```
Load("user"): read中找到 → 直接返回 (无锁！)
Load("role"): read中找到 → 直接返回 (无锁！)

性能：原子读取read → map查找 → 指针解引用
时间复杂度：O(1)，无锁竞争
```

**场景5：更新已存在的key（并发安全性分析）**
```go
m.Store("user", "bob")  // 更新现有key
```

**数据流转：**
```
1. 在read中找到"user"对应的entry
2. 调用entry.tryStore(&value)原子更新entry.p指针
3. 无需操作dirty，无需获取mu锁

read中的entry.p: "alice" → "bob" (原子更新)
```

**并发更新的安全性问题：**

你的疑问很对！让我们看看并发更新同一个key的情况：

```go
// 多个goroutine同时更新同一个key
go func() { m.Store("counter", 1) }()  // goroutine 1
go func() { m.Store("counter", 2) }()  // goroutine 2  
go func() { m.Store("counter", 3) }()  // goroutine 3
```

**entry.tryStore源码分析：**
```go
func (e *entry) tryStore(i *interface{}) bool {
    for {
        p := atomic.LoadPointer(&e.p)
        if p == expunged {
            return false  // 已被删除，需要走慢路径
        }
        if atomic.CompareAndSwapPointer(&e.p, p, unsafe.Pointer(i)) {
            return true   // 原子更新成功
        }
        // CAS失败，重试
    }
}
```

**并发更新的执行流程：**
```
时间线：T1    T2    T3    T4
协程1：  读p   CAS   成功
协程2：    读p   CAS   失败，重试，成功  
协程3：      读p   CAS   失败，重试，成功

最终结果：counter = 3 (最后成功的协程获胜)
```

**关键点解析：**

1. **内存安全**：使用CAS原子操作保证不会出现内存损坏
2. **无锁实现**：避免了获取互斥锁的开销
3. **竞态条件**：多个协程更新同一key时，结果不确定
4. **最后写入者获胜**：这是sync.Map的设计选择

**并发安全vs业务安全：**

```go
// sync.Map提供的是内存安全，不是业务逻辑安全
var m sync.Map
m.Store("balance", 100)

// 两个协程同时转账
go func() {
    val, _ := m.Load("balance")
    balance := val.(int)
    m.Store("balance", balance-50)  // 余额-50
}()

go func() {
    val, _ := m.Load("balance") 
    balance := val.(int)
    m.Store("balance", balance-30)  // 余额-30
}()

// 可能的结果：50 或 70，而不是期望的20
// 因为读取和写入之间存在竞态条件
```

**正确的并发更新方式：**

如果需要业务逻辑的原子性，应该：

```go
// 方案1：使用互斥锁保护业务逻辑
var mu sync.Mutex
var m sync.Map

func updateBalance(delta int) {
    mu.Lock()
    defer mu.Unlock()
    
    val, _ := m.Load("balance")
    balance := val.(int)
    m.Store("balance", balance+delta)
}

// 方案2：使用原子操作
var balance int64
func updateBalance(delta int64) {
    atomic.AddInt64(&balance, delta)
}

// 方案3：使用channel串行化
type BalanceManager struct {
    ch chan func()
    balance int
}

func (bm *BalanceManager) UpdateBalance(delta int) {
    done := make(chan struct{})
    bm.ch <- func() {
        bm.balance += delta
        close(done)
    }
    <-done
}
```

**总结：**
- sync.Map的更新操作确实无需获取互斥锁
- 但这只保证了**内存安全**，不保证**业务逻辑安全**  
- 多个goroutine并发更新同一key时，结果是不确定的
- 如果需要业务逻辑的原子性，需要额外的同步机制

**场景6：添加新key触发数据分离**
```go
m.Store("dept", "engineering")  // 新key
```

**数据流转：**
```
1. read中没有"dept"
2. 加锁，检查dirty是否为nil
3. dirty为nil，需要重建：将read中所有entry复制到dirty
4. 在dirty中添加新key
5. 设置amended=true

重建后：
read:  {
    m: {"user": &entry{p: "bob"}, "role": &entry{p: "admin"}},
    amended: true  // 标记dirty有新数据
}
dirty: {
    "user": &entry{p: "bob"},     // 共享同一个entry
    "role": &entry{p: "admin"},   // 共享同一个entry  
    "dept": &entry{p: "engineering"}  // 新entry
}
misses: 0
```

**并发安全机制：**

1. **读操作并发安全：**
   ```go
   // 多个goroutine同时读取，完全无锁
   go func() { m.Load("user") }()   // goroutine 1
   go func() { m.Load("role") }()   // goroutine 2
   go func() { m.Load("user") }()   // goroutine 3
   
   // 都是原子读取read，无竞争
   ```

2. **写操作并发安全：**
   ```go
   // 写操作通过mu互斥锁保护
   go func() { m.Store("key1", "val1") }()  // 只有一个能获得锁
   go func() { m.Store("key2", "val2") }()  // 其他等待
   ```

3. **读写并发安全：**
   ```go
   // 读写可以并发执行
   go func() { m.Load("user") }()      // 无锁读取read
   go func() { m.Store("new", "val") }() // 加锁操作dirty
   
   // 读操作不会被写操作阻塞！
   ```

**性能优势总结：**

| 操作场景 | 执行路径 | 性能特点 |
|---------|---------|----------|
| 读取已存在key | read map查找 | 无锁，O(1) |
| 更新已存在key | 原子更新entry.p | 无锁，O(1) |  
| 读取新key(miss) | 加锁查dirty | 有锁，但会触发优化 |
| 添加新key | 加锁操作dirty | 有锁，较慢 |
| 删除key | 标记删除 | 延迟处理，较快 |

**核心优化策略：**
1. **空间换时间**：维护read+dirty两套数据
2. **延迟同步**：通过miss计数延迟数据提升
3. **指针共享**：read和dirty共享entry指针，节省内存
4. **读写分离**：读操作走read(无锁)，写操作走dirty(有锁)
5. **批量提升**：一次性将dirty提升为read，摊销成本

这就是为什么sync.Map在读多写少的场景下性能优异的根本原因！

#### sync.Pool（对象池）底层实现

**核心设计思想：分层存储 + GC配合 + 无锁化**

**数据结构：**
```go
type Pool struct {
    noCopy noCopy
    
    local     unsafe.Pointer // 本地Pool数组，每个P一个
    localSize uintptr        // local数组大小
    
    victim     unsafe.Pointer // 上一轮的本地Pool数组
    victimSize uintptr        // victim数组大小
    
    New func() interface{}    // 创建新对象的函数
}

// 每个P的本地Pool
type poolLocal struct {
    poolLocalInternal
    pad [128 - unsafe.Sizeof(poolLocalInternal{})%128]byte
}

type poolLocalInternal struct {
    private interface{}   // 私有对象，只能当前P访问
    shared  poolChain     // 共享对象队列，其他P可以偷取
}
```

**分层存储机制：**

```
                 sync.Pool
                     │
        ┌────────────┼────────────┐
        │            │            │
    P0 local     P1 local     P2 local
    ┌─────────┐  ┌─────────┐  ┌─────────┐
    │private  │  │private  │  │private  │
    │shared   │  │shared   │  │shared   │
    └─────────┘  └─────────┘  └─────────┘
                     │
                 Work Stealing
```

**Get操作数据流：**
```go
func (p *Pool) Get() interface{} {
    // 1. 禁用抢占，获取当前P的本地Pool
    l, pid := p.pin()
    x := l.private
    l.private = nil
    if x == nil {
        // 2. 私有对象为空，从共享队列获取
        x, _ = l.shared.popHead()
        if x == nil {
            // 3. 本地都为空，尝试从其他P偷取
            x = p.getSlow(pid)
        }
    }
    runtime_procUnpin()
    
    // 4. 都没有，调用New创建
    if x == nil && p.New != nil {
        x = p.New()
    }
    return x
}
```

**Put操作数据流：**
```go
func (p *Pool) Put(x interface{}) {
    if x == nil {
        return
    }
    
    l, _ := p.pin()
    if l.private == nil {
        // 优先放入私有槽位
        l.private = x
        x = nil
    }
    if x != nil {  
        // 私有槽位已满，放入共享队列
        l.shared.pushHead(x)
    }
    runtime_procUnpin()
}
```

**Work Stealing（工作窃取）机制：**
```go
func (p *Pool) getSlow(pid int) interface{} {
    size := runtime_LoadAcquintptr(&p.localSize)
    locals := p.local
    
    // 从其他P的共享队列偷取对象
    for i := 0; i < int(size); i++ {
        l := indexLocal(locals, (pid+i+1)%int(size))
        if x, _ := l.shared.popTail(); x != nil {
            return x
        }
    }
    
    // 从victim中获取（上一轮GC保留的对象）
    size = atomic.LoadUintptr(&p.victimSize)
    if uintptr(pid) >= size {
        return nil
    }
    locals = p.victim
    l := indexLocal(locals, pid)
    if x := l.private; x != nil {
        l.private = nil
        return x
    }
    // ... 类似逻辑
}
```

**GC清理机制：**
```go
// GC时会调用poolCleanup
func poolCleanup() {
    for _, p := range allPools {
        // 将当前local移到victim
        p.victim = p.local
        p.victimSize = p.localSize
        
        // 清空当前local
        p.local = nil
        p.localSize = 0
    }
    
    // 清理上一轮的victim
    for _, p := range allPools {
        p.victimSize = 0
        p.victim = nil
    }
}
```

**性能优化技术：**
1. **无锁化**：通过P本地存储避免锁竞争
2. **Work Stealing**：负载均衡，充分利用对象
3. **Victim机制**：给对象第二次生命周期，减少GC压力
4. **内存对齐**：避免false sharing

#### Channel（通道）底层实现

**核心设计思想：CSP模型 + 队列 + 调度器集成**

**数据结构：**
```go
type hchan struct {
    qcount   uint           // 队列中数据个数
    dataqsiz uint           // 环形队列大小
    buf      unsafe.Pointer // 环形队列指针
    elemsize uint16         // 元素大小
    closed   uint32         // 关闭标志
    elemtype *_type         // 元素类型
    sendx    uint           // 发送索引
    recvx    uint           // 接收索引
    recvq    waitq          // 接收等待队列
    sendq    waitq          // 发送等待队列
    
    lock mutex              // 互斥锁
}

type waitq struct {
    first *sudog  // 等待队列头
    last  *sudog  // 等待队列尾
}

type sudog struct {
    g *g          // 等待的goroutine
    elem unsafe.Pointer // 数据指针
    // ... 其他字段
}
```

**Channel结构图：**
```
                 hchan
    ┌─────────────────────────────┐
    │ qcount=2, dataqsiz=4       │
    │ sendx=2, recvx=0           │
    ├─────────────────────────────┤
    │ buf: [elem0][elem1][ ][ ]  │ 环形缓冲区
    │       ↑recvx    ↑sendx     │
    ├─────────────────────────────┤
    │ sendq: G1 → G2 → nil       │ 发送等待队列
    │ recvq: G3 → nil            │ 接收等待队列
    └─────────────────────────────┘
```

**发送操作（ch <- v）数据流：**
```go
func chansend(c *hchan, ep unsafe.Pointer, block bool) bool {
    // 1. 快速路径：检查是否可以直接发送
    if !block && c.closed == 0 && full(c) {
        return false
    }
    
    lock(&c.lock)
    
    // 2. 通道已关闭
    if c.closed != 0 {
        unlock(&c.lock)
        panic("send on closed channel")
    }
    
    // 3. 有接收者等待，直接发送
    if sg := c.recvq.dequeue(); sg != nil {
        send(c, sg, ep, func() { unlock(&c.lock) })
        return true
    }
    
    // 4. 缓冲区有空间，放入缓冲区
    if c.qcount < c.dataqsiz {
        qp := chanbuf(c, c.sendx)
        typedmemmove(c.elemtype, qp, ep)
        c.sendx++
        if c.sendx == c.dataqsiz {
            c.sendx = 0  // 环形队列
        }
        c.qcount++
        unlock(&c.lock)
        return true
    }
    
    // 5. 阻塞发送：加入发送等待队列
    gp := getg()
    mysg := acquireSudog()
    mysg.elem = ep
    mysg.g = gp
    c.sendq.enqueue(mysg)
    
    gopark(chanparkcommit, unsafe.Pointer(&c.lock), ...)
    // goroutine被挂起，等待接收者唤醒
}
```

**接收操作（<-ch）数据流：**
```go
func chanrecv(c *hchan, ep unsafe.Pointer, block bool) (bool, bool) {
    // 1. 快速路径检查
    if !block && empty(c) {
        return false, false
    }
    
    lock(&c.lock)
    
    // 2. 通道关闭且为空
    if c.closed != 0 && c.qcount == 0 {
        unlock(&c.lock)
        return true, false
    }
    
    // 3. 有发送者等待，直接接收
    if sg := c.sendq.dequeue(); sg != nil {
        recv(c, sg, ep, func() { unlock(&c.lock) })
        return true, true
    }
    
    // 4. 缓冲区有数据，从缓冲区接收
    if c.qcount > 0 {
        qp := chanbuf(c, c.recvx)
        if ep != nil {
            typedmemmove(c.elemtype, ep, qp)
        }
        typedmemclr(c.elemtype, qp)
        c.recvx++
        if c.recvx == c.dataqsiz {
            c.recvx = 0
        }
        c.qcount--
        unlock(&c.lock)
        return true, true
    }
    
    // 5. 阻塞接收：加入接收等待队列
    gp := getg()
    mysg := acquireSudog()
    mysg.elem = ep
    mysg.g = gp
    c.recvq.enqueue(mysg)
    
    gopark(chanparkcommit, unsafe.Pointer(&c.lock), ...)
    // goroutine被挂起，等待发送者唤醒
}
```

**Select实现原理：**
```go
func selectgo(cas0 *scase) (int, bool) {
    // 1. 打乱case顺序，避免饥饿
    for i := 0; i < ncases; i++ {
        cas[i] = cas0[i]
    }
    pollorder := make([]uint16, ncases)
    for i := range pollorder {
        pollorder[i] = uint16(fastrandn(uint32(ncases)))
    }
    
    // 2. 按顺序加锁所有channel
    lockorder := make([]uint16, ncases)
    // ... 排序逻辑避免死锁
    
    // 3. 第一轮：检查是否有ready的case
    for _, casei := range pollorder {
        cas := &scases[casei]
        if cas.c.closed != 0 || cas.c.qcount != 0 || len(cas.c.sendq) != 0 {
            // 找到ready的case，执行并返回
        }
    }
    
    // 4. 第二轮：没有ready的case，注册到所有channel的等待队列
    gp := getg()
    for _, casei := range lockorder {
        cas := &scases[casei]
        c := cas.c
        sg := acquireSudog()
        sg.g = gp
        if cas.kind == caseRecv {
            c.recvq.enqueue(sg)
        } else {
            c.sendq.enqueue(sg)
        }
    }
    
    // 5. 挂起goroutine，等待任一channel就绪
    gopark(selparkcommit, nil, ...)
}
```

**调度器集成：**
- **gopark**：将goroutine从运行队列移除，状态改为等待
- **goready**：将goroutine重新加入运行队列，等待调度
- **sudog**：连接goroutine和channel的中间结构

**性能优化技术：**
1. **快速路径**：无锁检查常见情况
2. **直接发送**：有等待者时直接内存拷贝，跳过缓冲区
3. **批量唤醒**：close时批量唤醒所有等待者
4. **内存复用**：sudog对象池化复用

### 3. TCP服务器连接数限制因素

**问题：** TCP服务器有多个客户端连接，限制连接数的因素有哪些？

**答案：**

**主要限制因素：**

1. **文件描述符限制**
   ```bash
   # 查看当前限制
   ulimit -n
   
   # 修改限制
   ulimit -n 65536
   
   # 永久修改 /etc/security/limits.conf
   * soft nofile 65536
   * hard nofile 65536
   ```

2. **内存限制**
   - 每个连接需要内存：TCP缓冲区 + 应用层缓冲区
   - 默认TCP缓冲区：读写各几十KB
   - 大量连接会消耗大量内存

3. **端口号限制**
   - 客户端连接：可用端口数约65535个
   - 服务端：单个端口可接受大量连接

4. **系统内核参数**
   ```bash
   # 查看系统限制
   cat /proc/sys/net/core/somaxconn    # 监听队列长度
   cat /proc/sys/net/ipv4/tcp_max_syn_backlog  # SYN队列长度
   
   # 调整参数
   echo 65536 > /proc/sys/net/core/somaxconn
   ```

5. **应用程序设计**
   - 线程模型：每连接一线程 vs 事件驱动
   - 内存管理：连接池、缓冲区复用
   - 超时设置：及时释放死连接

**优化策略：**
- 使用epoll/kqueue等高效I/O模型
- 实现连接池管理
- 设置合理的超时时间
- 监控连接状态，及时清理

### 4. Load Average vs CPU使用率

**问题：** top命令能查看load和cpu使用率，这两者有什么区别？

**答案：**

**Load Average（负载平均值）：**
- **定义：** 系统在特定时间内的平均活跃进程数
- **计算：** 包括正在运行 + 等待运行 + 等待I/O的进程
- **时间维度：** 1分钟、5分钟、15分钟的平均值

**CPU使用率：**
- **定义：** CPU在特定时间内的繁忙程度百分比
- **计算：** (总时间 - 空闲时间) / 总时间 * 100%
- **时间维度：** 实时或短期平均

**关键区别：**

| 指标 | Load Average | CPU使用率 |
|------|-------------|----------|
| 反映内容 | 系统整体负载 | CPU繁忙程度 |
| 包含范围 | CPU + I/O等待 | 仅CPU计算 |
| 理想值 | ≤ CPU核心数 | < 100% |
| 问题诊断 | 系统瓶颈定位 | CPU性能分析 |

**典型场景分析：**
```bash
# 场景1：CPU密集型
load average: 8.0, 8.0, 8.0    # 高负载
%Cpu(s): 95.0 us, 5.0 sy       # 高CPU使用率

# 场景2：I/O密集型  
load average: 8.0, 8.0, 8.0    # 高负载
%Cpu(s): 10.0 us, 2.0 sy, 88.0 wa  # 低CPU使用率，高I/O等待

# 场景3：正常状态
load average: 2.0, 2.0, 2.0    # 正常负载(4核CPU)
%Cpu(s): 50.0 us, 5.0 sy       # 中等CPU使用率
```

### 5. Goroutine Panic传播

**问题：** goroutine A中启动了goroutine B，B里面出现了panic，A中是否可以recover到？

**答案：**

**结论：不可以！**

**原因：**
- **Panic不会跨goroutine传播**
- **Recover只能在同一个goroutine中捕获panic**
- 每个goroutine有独立的panic/recover机制

**代码示例：**
```go
func main() {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("主goroutine恢复:", r)  // 这里不会执行
        }
    }()
    
    go func() {
        panic("子goroutine panic")  // 这个panic无法被主goroutine捕获
    }()
    
    time.Sleep(time.Second)
    fmt.Println("主goroutine继续执行")  // 程序会崩溃，这里不会执行
}
```

**正确的处理方式：**
```go
func main() {
    done := make(chan bool)
    
    go func() {
        defer func() {
            if r := recover(); r != nil {
                fmt.Println("子goroutine恢复:", r)
            }
            done <- true
        }()
        
        panic("子goroutine panic")
    }()
    
    <-done
    fmt.Println("主goroutine继续执行")
}
```

**最佳实践：**
1. **每个goroutine都应该有自己的recover机制**
2. **使用channel通信goroutine的状态**
3. **实现supervisor模式监控子goroutine**

### 6. Go Context底层实现

**问题：** Go里面有context，能存多个kv，底层是怎么实现的？

**答案：**

**核心数据结构：**
```go
type Context interface {
    Deadline() (deadline time.Time, ok bool)
    Done() <-chan struct{}
    Err() error
    Value(key interface{}) interface{}
}

// valueCtx实现
type valueCtx struct {
    Context
    key, val interface{}
}
```

**底层实现原理：**

1. **链式结构：**
   ```go
   // 每个WithValue都创建一个新的valueCtx
   func WithValue(parent Context, key, val interface{}) Context {
       return &valueCtx{parent, key, val}
   }
   ```

2. **递归查找：**
   ```go
   func (c *valueCtx) Value(key interface{}) interface{} {
       if c.key == key {
           return c.val
       }
       return c.Context.Value(key)  // 递归查找父节点
   }
   ```

3. **结构示例：**
   ```
   WithValue(ctx, "user", "alice")
   └── WithValue(ctx, "role", "admin")  
       └── WithValue(ctx, "dept", "eng")
   
   查找"user"时：
   dept节点 → role节点 → user节点 ✓
   ```

**特点：**
- **不可变性：** 每次WithValue都创建新的context
- **链式查找：** 从当前节点向上递归查找
- **时间复杂度：** O(n)，n为链的深度
- **内存开销：** 每个key-value对应一个节点

**使用建议：**
```go
// 推荐：少量key-value
ctx = context.WithValue(ctx, "userID", 123)
ctx = context.WithValue(ctx, "traceID", "abc-123")

// 不推荐：大量key-value（考虑使用struct）
type RequestInfo struct {
    UserID  int
    TraceID string
    Role    string
    // ... 更多字段
}
ctx = context.WithValue(ctx, "requestInfo", RequestInfo{...})
```
