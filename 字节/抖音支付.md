### 1. MySQL脏读/幻读及解决方案

**问题：** 什么是脏读和幻读？如何解决？

**答案：**
- **脏读（Dirty Read）：** 一个事务读取了另一个事务未提交的数据
  - 事务A修改数据但未提交，事务B读取了这个未提交的数据
  - 如果事务A回滚，事务B读到的就是"脏数据"

- **幻读（Phantom Read）：** 一个事务在读取某个范围的记录时，另一个事务在该范围内插入了新记录
  - 事务A查询满足条件的记录数为N
  - 事务B插入一条满足条件的记录并提交
  - 事务A再次查询发现记录数变成了N+1

**解决方案：**
- **脏读：** 使用READ COMMITTED隔离级别或更高
假设事务 A 和 事务 B
数据 id=1, score = 100

事务A 执行：
UPDATE users SET score = 200 WHERE id = 1;
此时记录有两个版本，一个版本是 100，一个版本是 200。
版本 200 的记录中，DB_TRX_ID 是事务A的事务ID，假设为 100，DB_ROLL_PTR 指向版本 100 的记录。

事务 B 执行
select score from users where id = 1;
先读到 记录 200，readview 中会记录当前的活跃事务ID列表，由于事务A还没有提交，因此列表为 active_trx_ids = [100]。
又因为版本 200 的记录中，事务 ID 为 100，该事务为活跃事务，所以不可见。避免了脏读


- **幻读：** 使用SERIALIZABLE隔离级别，或在REPEATABLE READ下使用间隙锁

### 2. MVCC原理

**问题：** 什么是MVCC？它是如何工作的？

**答案：**
MVCC（Multi-Version Concurrency Control）多版本并发控制

**实现原理：**
- **版本链：** 每行记录都有多个版本，通过DB_TRX_ID、DB_ROLL_PTR形成版本链
- **ReadView：** 事务执行时生成快照，包含当前活跃事务ID列表
- **可见性判断：** 根据ReadView判断哪个版本的数据对当前事务可见

**核心字段：**
- `DB_TRX_ID`：创建/修改该记录的事务ID
- `DB_ROLL_PTR`：指向undo log中该记录的上一个版本
- `DB_ROW_ID`：行ID（如果表没有主键）

**可见性算法：**
```
if (DB_TRX_ID < min_trx_id) {
    // 记录创建时间早于ReadView，可见
    return visible;
} else if (DB_TRX_ID >= max_trx_id) {
    // 记录创建时间晚于ReadView，不可见
    return not_visible;
} else if (DB_TRX_ID in active_trx_ids) {
    // 创建该记录的事务还在活跃，不可见
    return not_visible;
} else {
    // 创建该记录的事务已提交，可见
    return visible;
}
```

### 3. 行锁/间隙锁实现

**问题：** MySQL中行锁和间隙锁是如何实现的？

**答案：**

**行锁（Record Lock）：**
- 锁定索引记录，防止其他事务修改该行
- 基于B+树索引实现，锁定叶子节点的具体记录
- 分为共享锁（S锁）和排他锁（X锁）

**间隙锁（Gap Lock）：**
- 锁定索引记录之间的间隙，防止其他事务在间隙中插入记录
- 只在REPEATABLE READ隔离级别下启用
- 用于解决幻读问题

**Next-Key Lock：**
- 行锁 + 间隙锁的组合
- 锁定记录本身以及记录前面的间隙
- 是InnoDB默认的锁定方式

**实现细节：**
```sql
-- 假设有索引值：10, 20, 30
-- 执行：SELECT * FROM table WHERE id = 15 FOR UPDATE

-- 会加Next-Key Lock：
-- Gap Lock: (10, 20)  -- 间隙锁
-- Record Lock: 20     -- 如果存在记录20的话
```

### 4. Redis主从复制原理

**问题：** Redis是如何实现主从复制的？

**答案：**

**复制过程：**
1. **建立连接：** 从节点向主节点发送PSYNC命令
2. **全量复制：** 主节点生成RDB快照，发送给从节点
3. **增量复制：** 主节点将写命令发送到复制缓冲区，异步发送给从节点

**详细流程：**
```
1. 从节点执行 SLAVEOF masterip masterport
2. 从节点发送 PING 命令测试连接
3. 主节点返回 PONG，连接建立成功
4. 从节点发送 PSYNC runid offset 命令
5. 主节点判断是全量复制还是增量复制
6. 全量复制：主节点执行 BGSAVE 生成RDB文件
7. 主节点将RDB文件发送给从节点
8. 从节点清空数据库，载入RDB文件
9. 主节点将缓冲区的写命令发送给从节点
10. 进入增量复制阶段
```

**关键概念：**
- **runid：** 主节点的运行ID，重启后会改变
- **offset：** 复制偏移量，用于判断主从数据一致性
- **复制缓冲区：** 环形缓冲区，存储最近的写命令

### 5. Redis跳表实现

**问题：** Redis中的跳表是如何实现的？为什么使用跳表？

**答案：**

**跳表结构：**
```c
typedef struct zskiplist {
    struct zskiplistNode *header, *tail;  // 头尾节点
    unsigned long length;                 // 节点数量
    int level;                           // 最大层数
} zskiplist;

typedef struct zskiplistNode {
    sds ele;                             // 成员对象
    double score;                        // 分值
    struct zskiplistNode *backward;      // 后退指针
    struct zskiplistLevel {
        struct zskiplistNode *forward;   // 前进指针
        unsigned long span;              // 跨度
    } level[];
} zskiplistNode;
```

**为什么使用跳表：**
1. **有序性：** 支持范围查询，时间复杂度O(logN)
2. **实现简单：** 相比红黑树更容易实现和理解
3. **内存友好：** 局部性好，缓存友好
4. **支持快速定位：** 可以快速跳到指定排名的元素

**应用场景：**
- 有序集合（ZSET）的底层实现
- 支持ZRANGE、ZRANK等命令

### 6. SQL题：求学生总成绩TOP5

**问题：** 使用GROUP BY+SUM+ORDER BY+LIMIT求学生总成绩TOP5

**答案：**
```sql
-- 假设有表结构：
-- students: id, name
-- scores: student_id, subject, score

SELECT 
    s.id,
    s.name,
    SUM(sc.score) as total_score
FROM students s
JOIN scores sc ON s.id = sc.student_id
GROUP BY s.id, s.name
ORDER BY total_score DESC
LIMIT 5;

-- 或者如果只需要总分：
SELECT 
    student_id,
    SUM(score) as total_score
FROM scores
GROUP BY student_id
ORDER BY total_score DESC
LIMIT 5;
```

### 7. 场景题：大文件小内存排序

**问题：** 大文件小内存，文件内存储数字，要求对文件内容进行排序

**答案：**

**解决方案：外部排序（External Sorting）**

**详细步骤：**

1. **分块读取和排序**
   ```
   - 读取能装入内存的数据块（如1GB）
   - 在内存中使用快速排序对数据块排序
   - 将排序后的数据块写入临时文件（如temp1.txt, temp2.txt...）
   - 重复直到处理完所有数据
   ```

2. **多路归并**
   ```
   - 计算能同时打开的文件数量（受内存限制）
   - 如果临时文件数量超过限制，进行多轮归并
   - 使用优先队列（最小堆）维护每个文件的当前最小值
   - 为每个文件分配固定大小的缓冲区
   - 每次从堆中取出最小值写入输出文件
   - 从对应文件读取下一个数字加入堆
   - 重复直到所有文件处理完
   ```


**具体示例（1G内存，10G文件）：**
```
假设：
- 内存限制：1G
- 文件大小：10G
- 每个数字4字节

第一阶段：
- 每次读取250M数据进行排序（预留空间）
- 生成40个临时文件

第二阶段：
- 每个文件缓冲区64KB
- 可同时打开约15个文件（1G/64KB ≈ 16000，预留一些空间）
- 第一轮：40个文件分成3批，每批15个，生成3个归并文件
- 第二轮：3个文件一次性归并完成

内存使用：
- 15个文件 × 64KB = 960KB
- 输出缓冲区：64KB
- 堆和其他开销：< 1MB
- 总计：< 2MB（远小于1G限制）
```

**复杂度分析：**
- **时间复杂度：** O(N log N)，其中N为总记录数
- **空间复杂度：** O(M)，其中M为内存限制
- **I/O复杂度：** 每个数字读写3次（原文件→临时文件→输出文件）

**关键问题解答：内存控制**

针对"1G内存，10G文件，同时打开所有临时文件会爆内存"的疑惑：

**核心解决方案：**
1. **缓冲区控制：** 不是完全加载文件，而是为每个文件分配固定缓冲区（如64KB）
2. **堆只存当前值：** 堆中只维护每个文件的当前最小值，不是所有数据
3. **分批归并：** 如果临时文件太多，分多轮进行归并

**详细工作流程：**
```
初始化阶段：
- 打开40个文件，每个分配64KB缓冲区
- 从每个文件读取第一个数字到堆中
- 堆大小：40个元素

归并过程（循环）：
1. 从堆顶取出最小值 (min_val, file_idx)
2. 将 min_val 写入输出文件
3. 从 file_idx 对应的文件读取下一个数字
4. 如果成功读取，将新数字压入堆
5. 重复直到所有文件读完

关键点：堆的大小始终等于文件数量，与文件大小无关！
```

**实际内存使用：**
```
以40个临时文件为例：
- 文件缓冲区：40 × 64KB = 2.5MB
- 输出缓冲区：64KB
- 堆结构：40个元素 × 12字节 ≈ 480字节
- 总计：< 3MB（远小于1G限制）
```

**堆结构详解：**
堆并不加载所有数据！它只维护每个文件的当前最小值：
```
堆中只有40个元素（对应40个文件）：
[
  (123, file_0),  // 文件0的当前最小值是123
  (456, file_1),  // 文件1的当前最小值是456
  (789, file_2),  // 文件2的当前最小值是789
  ...
]

每个元素包含：
- 数值：4字节（int）
- 文件索引：4字节（int）  
- Python对象开销：约4字节
总计：约12字节/元素

具体执行示例：
假设有3个临时文件：
- temp1.txt: [1, 4, 7, 10]
- temp2.txt: [2, 5, 8, 11]  
- temp3.txt: [3, 6, 9, 12]

执行过程：
初始化：堆 = [(1, 0), (2, 1), (3, 2)]
步骤1：取出(1, 0)，写入1，从文件0读取4，堆 = [(2, 1), (3, 2), (4, 0)]
步骤2：取出(2, 1)，写入2，从文件1读取5，堆 = [(3, 2), (4, 0), (5, 1)]
步骤3：取出(3, 2)，写入3，从文件2读取6，堆 = [(4, 0), (5, 1), (6, 2)]
...依此类推

堆始终只有3个元素，即使文件很大！


### 8. Redis IO 多路复用

**问题：** Redis IO 多路复用是如何实现的？

**答案：**

**什么是IO多路复用：**
IO多路复用是一种IO模型，允许单个线程同时监听多个文件描述符（socket连接），当其中任何一个准备好进行读写操作时，就通知程序进行处理。

**Redis的实现方式：**
Redis使用Reactor模式 + IO多路复用，根据不同操作系统选择最优实现：
- **Linux：** epoll
- **macOS/FreeBSD：** kqueue  
- **Windows：** select

**核心工作流程：**
```
1. Redis主线程启动事件循环
2. 注册监听socket到epoll实例
3. 调用epoll_wait()等待事件
4. 当有客户端连接或数据到达时，epoll返回就绪的socket列表
5. Redis依次处理每个就绪的socket（读取命令、执行、返回结果）
6. 回到步骤3，继续等待下一批事件
```

**为什么快？关键优势：**

1. **避免线程切换开销**
   ```
   传统多线程模型：
   - 每个连接一个线程
   - 1000个连接 = 1000个线程
   - 线程切换开销：每次2-20μs
   - 内存开销：每线程约8MB栈空间
   
   Redis单线程模型：
   - 1个线程处理所有连接
   - 无线程切换开销
   - 内存开销极小
   ```

2. **减少系统调用次数**
   ```
   传统模型（每个连接单独处理）：
   - 1000个连接 = 1000次read()系统调用
   
   epoll模型：
   - 1次epoll_wait()返回所有就绪连接
   - 批量处理，系统调用次数大幅减少
   ```

3. **CPU缓存友好**
   ```
   - 单线程顺序处理，CPU缓存命中率高
   - 没有多线程竞争，无需锁同步
   - 指令流水线更高效
   ```

4. **避免惊群效应**
   ```
   多进程模型：
   - 新连接到达时，所有进程被唤醒
   - 只有一个进程能处理，其他进程白跑
   
   单线程模型：
   - 只有一个线程，不存在惊群问题
   ```

**性能对比数据：**
```
压测环境：4核CPU，8GB内存
并发连接：10000个客户端，每秒100000请求

多线程模型：
- CPU使用率：85%（大量时间用于线程切换）
- QPS：~50000
- 延迟：平均5ms

Redis单线程+IO多路复用：
- CPU使用率：25%  
- QPS：~100000+
- 延迟：平均0.1ms
```

**监听就绪文件描述符的底层实现原理：**

**核心数据结构：**
- **红黑树**：存储所有被监听的socket连接（文件描述符）
- **就绪队列**：链表，存储已经就绪的连接
- **等待队列**：存储阻塞等待的进程

**工作流程：**

1. **注册监听**（epoll_ctl ADD）
   - 把socket文件描述符插入红黑树
   - 向socket注册一个回调函数
   - 红黑树按fd编号排序，查找速度O(log n)

2. **中断驱动事件通知**（中断上下文）
   - 网卡收到数据包 → 硬件中断
   - 内核找到对应socket → 调用epoll注册的回调函数
   - 回调函数把socket加入就绪队列
   - **唤醒阻塞在epoll_wait的进程**（关键！）
   - **注意：中断处理只负责"通知"，不处理具体数据**

3. **进程被唤醒，处理就绪事件**（进程上下文）
   - 应用程序调用epoll_wait()从就绪队列取出socket列表
   - **返回到用户空间，应用程序拿到就绪的fd**
   - **应用程序调用read()/recv()真正读取数据**
   - **应用程序处理数据（如Redis解析命令、执行、返回结果）**

**关键时机：只有当应用程序主动调用epoll_wait()时，才会处理就绪队列！**

**完整的数据处理流程：**
```
1. 客户端发送数据
2. 网卡收到 → 硬件中断
3. 中断处理：socket加入就绪队列 + 唤醒Redis进程
4. Redis进程被唤醒，继续执行事件循环
5. Redis调用epoll_wait() → 获取就绪的socket列表
6. Redis遍历每个就绪socket，调用read()读取数据
7. Redis解析命令、执行、调用write()返回结果
8. 回到步骤4，继续等待下一批事件
```

**Redis快和红黑树的关系：**

**传统select模型的问题：**
- 每次都要遍历所有socket（O(n)复杂度）
- 1万个连接就要检查1万次，99%都是无效检查
- 大量CPU时间浪费在轮询上

**epoll + 红黑树的优势：**
- **红黑树管理连接**：O(log n)时间找到任意连接，1万个连接最多查找14次
- **中断驱动**：只有真正有数据的socket才会触发回调，没有无效轮询
- **就绪队列**：epoll_wait直接返回就绪的socket，不遍历红黑树

**为什么选择红黑树而不是哈希表：**

**哈希表的问题：**
- **内存浪费**：需要预分配大量桶空间，利用率低
  - 1万连接可能需要分配10万个桶位置
  - 大部分桶都是空的，内存浪费严重
- **哈希冲突**：多个fd可能映射到同一个桶
  - 冲突时性能退化，最坏情况O(n)
  - 需要额外的冲突处理机制（链表/开放寻址）
- **扩容开销**：连接数增长时需要rehash
  - 重新计算所有fd的哈希值
  - 数据迁移过程中性能抖动
- **缓存不友好**：桶分散在内存各处，缓存命中率低

**红黑树的优势：**
- **内存精确**：按需分配，每个连接只占用必要的节点空间
- **性能稳定**：始终保证O(log n)，没有最坏情况退化
- **缓存友好**：相邻节点在内存中相对集中，提高缓存命中率
- **无冲突**：基于比较的数据结构，不存在哈希冲突问题

**实际性能对比：**
```
场景：10000个并发连接的epoll实例

哈希表实现：
- 预分配：16384个桶（负载因子0.75）
- 内存占用：16384 × 8字节 = 128KB（仅桶数组）
- 冲突处理：额外链表节点开销
- 查找：平均O(1)，冲突时退化

红黑树实现：
- 按需分配：10000个节点
- 内存占用：10000 × 64字节 = 640KB（包含完整节点）
- 查找：稳定O(log 10000) ≈ 14次比较
- 缓存命中率更高，实际性能接近哈希表
```

**Linux内核的考量：**
1. **内存是珍贵资源**：服务器可能有成千上万个epoll实例
2. **稳定性优于极致性能**：宁要稳定的O(log n)，不要不可控的O(1)
3. **实现复杂度**：红黑树逻辑更清晰，哈希表冲突处理复杂
4. **实际差距不大**：现代CPU上，14次内存访问 vs 1次内存访问的差距很小

**实际性能对比：**
```
10000并发连接场景：

传统select：
- 每次轮询10000个socket
- CPU大部分时间用于无效检查
- 延迟随连接数线性增长

epoll + 红黑树：
- 红黑树管理：最多14次查找定位任意连接
- 中断驱动：只处理真正就绪的连接
- 延迟几乎不随连接数增长
```

**关键点：红黑树解决了"从海量连接中快速定位"的问题，中断机制解决了"避免无效轮询"的问题，两者结合让Redis能以极低开销处理大量并发连接。**

**Redis事件循环伪代码：**
```c
void aeMain(aeEventLoop *eventLoop) {
    eventLoop->stop = 0;
    while (!eventLoop->stop) {
        // 如果有定时事件即将执行，计算等待时间
        if (eventLoop->maxfd != -1 || 
            ((tvp = aeSearchNearestTimer(eventLoop)) != NULL)) {
            
            // 调用IO多路复用函数等待事件
            numevents = aeApiPoll(eventLoop, tvp);
            
            // 处理文件事件（网络IO）
            for (j = 0; j < numevents; j++) {
                aeFileEvent *fe = &eventLoop->events[eventLoop->fired[j].fd];
                if (fe->mask & eventLoop->fired[j].mask & AE_READABLE) {
                    fe->rfileProc(eventLoop, fd, fe->clientData, mask);
                }
                if (fe->mask & eventLoop->fired[j].mask & AE_WRITABLE) {
                    fe->wfileProc(eventLoop, fd, fe->clientData, mask);
                }
            }
        }
        
        // 处理时间事件（定时任务）
        processTimeEvents(eventLoop);
    }
}
```

**关键性能优化：**
1. **就绪连接批量处理**：一次epoll_wait()返回多个就绪连接
2. **边缘触发模式(ET)**：减少重复通知，提高效率
3. **零拷贝技术**：减少数据在用户态和内核态之间的拷贝
4. **连接复用**：客户端连接池减少连接建立开销

**适用场景和限制：**
- **适用：** 高并发、I/O密集型应用
- **限制：** CPU密集型操作会阻塞整个事件循环
- **解决：** Redis 6.0引入多线程处理网络I/O，但命令执行仍是单线程
