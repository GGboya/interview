### 1. MySQL死锁的场景

**问题：** MySQL死锁的场景有哪些？

**答案：**

**死锁定义：** 两个或多个事务相互等待对方释放锁，形成循环等待。

**常见死锁场景：**

#### 场景1：不同顺序加锁
```sql
-- 事务A
BEGIN;
UPDATE users SET name='Alice' WHERE id=1;  -- 锁住id=1
UPDATE users SET name='Alice' WHERE id=2;  -- 等待id=2的锁

-- 事务B  
BEGIN;
UPDATE users SET name='Bob' WHERE id=2;    -- 锁住id=2
UPDATE users SET name='Bob' WHERE id=1;    -- 等待id=1的锁，死锁！
```

#### 场景2：索引不当导致的范围锁冲突
```sql
-- 假设age字段无索引
-- 事务A
UPDATE users SET status=1 WHERE age=25;    -- 全表扫描，锁住多行

-- 事务B
UPDATE users SET status=2 WHERE age=30;    -- 全表扫描，与A锁冲突
```

#### 场景3：Gap Lock导致的死锁
```sql
-- 在REPEATABLE READ隔离级别下
-- 事务A
SELECT * FROM users WHERE id BETWEEN 5 AND 10 FOR UPDATE;

-- 事务B  
INSERT INTO users (id, name) VALUES (7, 'test');  -- 被gap lock阻塞

-- 事务A
INSERT INTO users (id, name) VALUES (8, 'test2'); -- 死锁
```

#### 场景4：外键约束死锁
```sql
-- 父表orders，子表order_items
-- 事务A
UPDATE orders SET status='paid' WHERE id=1;        -- 锁住orders.id=1
INSERT INTO order_items (order_id, product) VALUES (2, 'book'); -- 需要检查orders.id=2

-- 事务B
UPDATE orders SET status='paid' WHERE id=2;        -- 锁住orders.id=2  
INSERT INTO order_items (order_id, product) VALUES (1, 'pen');  -- 需要检查orders.id=1，死锁
```

**避免死锁的策略：**
1. **固定加锁顺序**：所有事务按相同顺序访问资源
2. **缩短事务时间**：减少锁持有时间
3. **降低隔离级别**：使用READ COMMITTED避免gap lock
4. **添加合适索引**：避免全表扫描
5. **使用SELECT FOR UPDATE NOWAIT**：立即返回而不等待

### 2. Redis集群主从选举机制

**问题：** Redis集群主从选举，根据什么选主节点？

**答案：**

**Redis Sentinel选举机制：**

#### 选举触发条件
1. **主节点下线**：Sentinel检测到master不可达
2. **手动故障转移**：SENTINEL FAILOVER命令
3. **配置更改**：主从角色变更

#### 选举过程详解

**第一阶段：发现故障**
```
1. Sentinel每秒ping主节点
2. 超过down-after-milliseconds时间无响应
3. 标记为主观下线(SDOWN)
4. 通知其他Sentinel节点
```

**第二阶段：确认故障**
```
1. 收集其他Sentinel的意见
2. 达到quorum数量的Sentinel确认下线
3. 标记为客观下线(ODOWN)
4. 开始故障转移流程
```

**第三阶段：选举Leader Sentinel**
```
1. 每个Sentinel向其他Sentinel发送SENTINEL is-master-down-by-addr命令
2. 请求自己成为Leader
3. 收到超过一半Sentinel同意的成为Leader
4. Leader Sentinel执行故障转移
```

**第四阶段：选择新主节点**

**选择标准（按优先级）：**

#### 第一轮：健康状态过滤
```
1. 排除下线和断线的从节点
2. 排除5秒内没有回复INFO命令的从节点  
3. 排除与原主节点断线超过down-after-milliseconds*10毫秒的从节点
```

#### 第二轮：优先级评定
**slave-priority（从节点优先级）**
- **默认值：** 100
- **配置方式：** 
  ```bash
  # redis.conf中配置
  replica-priority 100
  
  # 运行时动态配置
  CONFIG SET replica-priority 50
  ```
- **评定规则：** 数值越小优先级越高
- **特殊值：** 设为0表示永不提升为主节点

**使用场景：**
```
高性能服务器：   replica-priority 10  (高优先级)
普通服务器：     replica-priority 100 (默认优先级)  
备用服务器：     replica-priority 200 (低优先级)
只读从节点：     replica-priority 0   (永不提升)
```

#### 第三轮：数据完整性评定
**replication offset（复制偏移量）**
- **含义：** 从节点已同步的数据量
- **评定规则：** 偏移量越大说明数据越新，优先级越高
- **查看方式：**
  ```bash
  # 在从节点执行
  INFO replication
  
  # 输出示例
  master_repl_offset:1000
  slave_repl_offset:998    # 落后2个字节
  ```

#### 第四轮：节点标识评定
**run_id（运行时ID）**
- **含义：** Redis实例启动时生成的40位随机字符串
- **评定规则：** 字典序最小的优先（确保选举结果的确定性）
- **查看方式：**
  ```bash
  INFO server | grep run_id
  # 输出：run_id:a1b2c3d4e5f6...
  ```

**完整选举算法伪代码：**
```python
def select_new_master(slaves):
    # 第一步：过滤不健康的从节点
    healthy_slaves = []
    for slave in slaves:
        if (slave.is_online and 
            slave.last_info_reply < 5000 and
            slave.master_link_down_time < down_after_ms * 10):
            healthy_slaves.append(slave)
    
    if not healthy_slaves:
        return None
    
    # 第二步：按多个维度排序
    healthy_slaves.sort(key=lambda s: (
        s.replica_priority,     # 1. 优先级（越小越优先）
        -s.repl_offset,        # 2. 复制偏移量（越大越优先）
        s.run_id               # 3. run_id（字典序越小越优先）
    ))
    
    return healthy_slaves[0]
```

**Redis vs K8s调度算法对比：**

#### Redis主节点选择（静态为主）
**优点：**
- 简单快速，选举时间短（毫秒级）
- 可预测性强，结果确定
- 运维可控，人工干预容易

**缺点：**
- 缺乏动态感知能力
- 不考虑实时系统状态
- 无法适应复杂的部署环境

#### K8s Pod调度（动态感知）
**调度流程：**
```go
// K8s调度器的核心流程
func (sched *Scheduler) scheduleOne(ctx context.Context) {
    // 1. 预选阶段 - 过滤不符合条件的节点
    feasibleNodes := sched.findNodesThatFitPod(pod)
    
    // 2. 优选阶段 - 对可行节点打分排序
    priorityList := sched.prioritizeNodes(pod, feasibleNodes)
    
    // 3. 选择最优节点
    selectedNode := selectHost(priorityList)
    
    // 4. 绑定Pod到节点
    sched.bind(pod, selectedNode)
}
```

**K8s动态检测维度：**
```yaml
调度策略：
  资源维度：
    - CPU使用率和可用量
    - 内存使用率和可用量  
    - 磁盘空间和IO性能
    - 网络带宽和延迟
    - GPU、存储等扩展资源
  
  拓扑维度：
    - 节点亲和性 (NodeAffinity)
    - Pod亲和性 (PodAffinity) 
    - Pod反亲和性 (PodAntiAffinity)
    - 拓扑域感知 (TopologySpreadConstraints)
  
  策略维度：
    - 污点容忍 (Taints/Tolerations)
    - 节点选择器 (NodeSelector)
    - 优先级类 (PriorityClass)
    - 抢占调度 (Preemption)
```

**为什么Redis选择了简单的算法？**

#### 设计理念差异
| 维度 | Redis | K8s |
|------|-------|-----|
| 目标 | 高性能数据库 | 通用容器编排平台 |
| 场景 | 故障转移（紧急情况） | 日常调度（计划性） |
| 时间要求 | 毫秒级决策 | 秒级调度 |
| 复杂度 | 简单可靠 | 灵活智能 |

#### 故障转移的特殊性
```
Redis故障转移场景：
- 主节点已经宕机，需要紧急恢复服务
- 时间窗口极其有限（毫秒级）
- 任何复杂的检测都可能导致服务中断延长
- 简单可靠比完美选择更重要

K8s调度场景：
- 正常的资源分配过程
- 可以花费时间做最优决策
- 调度失败可以重试
- 追求资源利用率最大化
```

#### Redis的权衡考虑
1. **可靠性优先**：简单算法不容易出错
2. **速度优先**：减少选举时间，快速恢复服务
3. **运维友好**：行为可预测，便于故障排查
4. **历史兼容**：保持向后兼容性

**Redis Cluster选举机制：**

在Redis Cluster模式下，选举流程：
```
1. 从节点检测到主节点FAIL状态
2. 等待一个随机延迟时间（避免同时选举）
3. 向集群广播FAILOVER_AUTH_REQUEST
4. 其他主节点投票（每个epoch只能投一票）
5. 获得超过一半主节点投票的从节点成为新主节点
```

### 3. Linux命令执行过程

**问题：** Linux执行一个命令，发生了什么？

**答案：**

**完整执行流程：**

#### 1. 命令输入和解析
```bash
$ ls -la /home
```

**Shell解析过程：**
```
1. 读取用户输入
2. 词法分析：分割成token [ls] [-la] [/home]
3. 语法分析：识别命令、选项、参数
4. 变量展开：$HOME、环境变量替换
5. 通配符展开：*、?等
6. 命令查找：在PATH中查找ls可执行文件
```

#### 2. 进程创建
```c
// Shell调用系统调用
pid_t pid = fork();  // 创建子进程

if (pid == 0) {
    // 子进程
    execve("/bin/ls", argv, envp);  // 执行程序
} else {
    // 父进程(Shell)
    wait(&status);  // 等待子进程完成
}
```

#### 3. 程序加载（execve系统调用）
```
1. 内核检查可执行文件格式（ELF）
2. 创建新的内存空间
3. 加载程序段：
   - .text段（代码）
   - .data段（已初始化数据）
   - .bss段（未初始化数据）
4. 设置堆和栈
5. 加载动态链接库
6. 设置程序入口点
```

#### 4. 内存布局
```
高地址
┌─────────────┐
│    Stack    │ 栈（向下增长）
├─────────────┤
│     ...     │
├─────────────┤
│    Heap     │ 堆（向上增长）
├─────────────┤
│    .bss     │ 未初始化数据
├─────────────┤
│    .data    │ 已初始化数据
├─────────────┤
│    .text    │ 程序代码
└─────────────┘
低地址
```

#### 5. 文件系统操作
```c
// ls命令的核心操作
```

#### 6. 系统调用链路
```
用户空间：ls命令
    ↓ (系统调用)

    ↓ VFS层
    ↓ 文件系统层(ext4/xfs)
    ↓ 块设备层
    ↓ 设备驱动

```

#### 7. 进程状态变化
```
创建 → 就绪 → 运行 → 阻塞(I/O) → 就绪 → 运行 → 结束
```

#### 8. 资源清理
```
1. 关闭打开的文件描述符
2. 释放内存空间
3. 释放进程控制块(PCB)
4. 向父进程发送SIGCHLD信号
5. 父进程调用wait()回收子进程
```

### 4. TCP vs UDP 对比

**问题：** TCP和UDP的区别？

**答案：**

**核心区别对比：**

| 特性 | TCP | UDP |
|------|-----|-----|
| 连接性 | 面向连接 | 无连接 |
| 可靠性 | 可靠传输 | 不可靠传输 |
| 顺序性 | 保证顺序 | 不保证顺序 |
| 流量控制 | 有（滑动窗口） | 无 |
| 拥塞控制 | 有 | 无 |
| 头部开销 | 20-60字节 | 8字节 |
| 传输速度 | 慢 | 快 |
| 应用场景 | 文件传输、网页、邮件 | 视频、游戏、DNS |

**TCP详细机制：**

#### 三次握手
```
客户端                    服务端
   │                        │
   │──── SYN seq=x ────────→│
   │                        │
   │←── SYN-ACK seq=y,ack=x+1 ──│
   │                        │
   │──── ACK seq=x+1,ack=y+1 ──→│
   │                        │
   └── 连接建立 ──────────────┘
```

#### 四次挥手
```
客户端                    服务端
   │                        │
   │──── FIN seq=m ────────→│
   │                        │
   │←──── ACK ack=m+1 ──────│
   │                        │
   │←──── FIN seq=n ────────│
   │                        │
   │──── ACK ack=n+1 ──────→│
   │                        │
   └── 连接关闭 ──────────────┘
```

#### 可靠性保证
```c
// 超时重传
struct tcp_timer {
    unsigned long timeout;
    int retrans_count;
};

// 滑动窗口
struct tcp_window {
    uint32_t send_una;     // 最早未确认序号
    uint32_t send_nxt;     // 下次发送序号
    uint32_t send_wnd;     // 发送窗口大小
    uint32_t recv_nxt;     // 期望接收序号
};
```

**UDP特点：**
```c
// UDP头部结构
struct udphdr {
    uint16_t source;      // 源端口
    uint16_t dest;        // 目标端口  
    uint16_t len;         // 长度
    uint16_t check;       // 校验和
};

// 简单发送
sendto(sockfd, data, len, 0, &addr, sizeof(addr));
```

**使用场景选择：**

**选择TCP的场景：**
- 数据完整性要求高：文件传输、数据库同步
- 顺序性要求：网页浏览、邮件发送
- 可靠性优先：金融交易、支付系统

**选择UDP的场景：**
- 实时性要求高：在线游戏、视频直播
- 简单请求-响应：DNS查询、DHCP
- 广播/组播：网络发现、路由协议

### 5. 浏览器访问网站的完整过程

**问题：** 输入www.baidu.com，发生了什么？

**答案：**

**完整流程详解：**

#### 1. URL解析
```
输入：www.baidu.com
解析结果：
- 协议：http（默认）
- 主机：www.baidu.com  
- 端口：80（默认）
- 路径：/（默认）
```

#### 2. DNS域名解析
```
查询顺序：
1. 浏览器缓存
2. 操作系统缓存  
3. 路由器缓存
4. ISP DNS服务器
5. 根域名服务器
6. 顶级域服务器(.com)
7. 权威域名服务器(baidu.com)

返回：39.156.66.10（百度IP地址之一）
```

**DNS解析过程：**
```
1. 浏览器 → 本地DNS服务器："www.baidu.com的IP是什么？"
2. 本地DNS → 根服务器："哪个服务器负责.com？"
3. 根服务器 → 本地DNS："向a.gtld-servers.net查询"
4. 本地DNS → .com服务器："哪个服务器负责baidu.com？"
5. .com服务器 → 本地DNS："向ns1.baidu.com查询"
6. 本地DNS → ns1.baidu.com："www.baidu.com的IP？"
7. ns1.baidu.com → 本地DNS："39.156.66.10"
8. 本地DNS → 浏览器："39.156.66.10"
```

#### 3. 建立TCP连接
```
客户端(浏览器)                百度服务器(39.156.66.10:80)
      │                              │
      │────── SYN ─────────────────→ │
      │                              │
      │ ←───── SYN+ACK ─────────────  │
      │                              │
      │────── ACK ─────────────────→ │
      │                              │
      └─── TCP连接建立 ──────────────┘
```

#### 4. 发送HTTP请求
```http
GET / HTTP/1.1
Host: www.baidu.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8
Accept-Language: zh-CN,zh;q=0.8,en-US;q=0.5,en;q=0.3
Accept-Encoding: gzip, deflate
Connection: keep-alive
```

#### 5. 服务器处理请求
```
1. 反向代理(Nginx)接收请求
2. 负载均衡器分发到后端服务器
3. Web服务器(Apache/Nginx)处理
4. 应用程序(PHP/Java)执行业务逻辑
5. 数据库查询(MySQL/Redis)
6. 生成HTML响应
```

#### 7. 浏览器解析渲染
```
1. HTML解析 → DOM树
2. CSS解析 → CSSOM树
3. JavaScript执行
4. DOM + CSSOM → 渲染树
5. 布局计算（Layout/Reflow）
6. 绘制（Paint）
7. 合成（Composite）
```

**渲染流程：**
```
HTML → 词法分析 → 语法分析 → DOM树
                                ↓
CSS → 词法分析 → 语法分析 → CSSOM树
                                ↓
                    DOM树 + CSSOM树 → 渲染树
                                ↓
                            布局计算
                                ↓
                            绘制显示
```

#### 8. 资源加载
```

- 图片资源
- 字体文件
每个资源都重复HTTP请求过程
```
